# Automatic EP News website → Reel handoff

During the **normal website article PR**, after the final 1600×900 image is uploaded and verified in public Google Drive, include one `editorial-reel-inputs/<slug>.json` file. This is editorial source data, **not** a claim that the website is already live. It must contain `slug` (matching the website article ID), `article_script` (e.g. `content/example-story.js`), `headline`, `facebook_description`, `drive_file_id`, `fact_checked:true`, `image_verified:true`, `approved_for_reel:true`, `automatic_reel:true`, `website_published:false`, and optional music/duration.

The story and image still go through the existing publishing gate, Cloudflare preview, and explicit human approval. **Only after the website PR is merged** does the new `post-publication-reel.yml` workflow run. It checks that the live homepage references the article script, the live script contains the expected ID, and the live article is marked published. It retries while Cloudflare deploys; a failed check blocks Reel preparation.

After successful verification it runs `scripts/prepare_publication_reel.py`, pushes the generated manifest to a separate branch, and attempts to open a PR. **The user must approve and merge this generated PR.** That merge triggers the existing MP4 preview generator. The repository must allow GitHub Actions to create pull requests; otherwise the job reports an error and a maintainer must enable the repository's Actions setting. This workflow handles one new approved story input per merge; it fails rather than guessing when multiple are added.

Never put `website_published:true` in the editorial input; only the live verification step sets it. This checks live registration and published status, not factual accuracy, Drive permissions, or whether the image displays correctly; those remain editorial and website publication gates. No automatic Meta drafts or public Facebook publishing. Music preferences are metadata only.
